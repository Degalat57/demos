# Pharma Batch Review & Release — Process Intelligence demo

A working proof-of-concept that reconstructs the batch review & release process from an SAP-style extract, computes release KPIs deterministically, explains outcome KPIs through process KPIs, scores process maturity in an explainable way, tests whether an intervention worked, and answers questions through a copilot whose every number is traced to a tool call. **All data is synthetic.**

> **Honesty notes.** Every batch, site, product, user role and event is generated by `src/brpi/generate.py`. The framework mapping (EU GMP Annex 16, ICH Q9(R1), ICH Q10, APQC Life Sciences PCF) is a **draft for sign-off by a qualified GMP / QA expert**; it paraphrases public texts and is not regulatory advice. This is decision support for Process Excellence and Quality. It never decides batch disposition, closes deviations, approves CAPA or writes to GxP records. No pharma delivery track record is claimed; the demo shows the method and the engineering.

## What it shows

| Spec screen | Where | What is computed |
|---|---|---|
| 1 Framework & process selection | tab 1, **ANALYZE MY PROCESS** | process health score, KPI table (current · target · gap · trend), top issues, framework assessment (aligned / investigate / missing evidence), top 3 opportunities |
| 2 Executive cockpit | tab 2, "View as" L1-L4 | maturity, outcome and process KPIs, critical-path driver decomposition, trend, site maturity, framework gaps, opportunities, open batches at cut-off |
| 3 Process explorer | tab 3 | process map (frequency / median waiting), expected vs actual (declarative conformance), variants, bottleneck transitions, loops, hand-offs, one batch traced to its source rows, data-quality report |
| 4 KPI & benchmark | tab 4 | every KPI with actual · target · internal best · gap · trend · coverage; drilldown outcome → process → activity |
| 5 Quality intelligence | tab 5 | facts vs hypotheses, fast vs slow batches, deviation patterns, rework patterns, site/product differences |
| 6 Improvement & maturity | tab 6 | maturity change attributed per dimension, tracker (opportunity → … → status), interactive pre/post test with control site |
| 7 Copilot | tab 7 + "Ask Copilot" on every screen | scripted conversation executed against the real tools, with traces; live deterministic Q&A on the current filters |

Filters (site, product, period) and the **Exclude exceptional events** toggle recompute everything in the browser.

## How to run

```sh
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt          # pandas, numpy, scipy, pytest
PYTHONPATH=src python -m brpi build      # generate extract -> event log -> KPIs -> data/processed + assets/data.js
PYTHONPATH=src python -m brpi transcript # print the copilot conversation with tool traces
python -m pytest -q                      # 28 tests (hand-built fixtures + full pipeline + JS/Python parity)
python3 -m http.server 8000              # open http://localhost:8000/  (index.html also works from file://)
```

`python -m brpi generate` writes only the synthetic CSV extract (`data/raw/`). The seed is fixed, so builds are reproducible byte for byte.

No LLM is used anywhere (spec Option C). The copilot tool layer is the integration point for an approved enterprise LLM endpoint (Option A): the model would choose tools and phrase results; numbers stay deterministic and the grounding check still applies.

## Data model

**Case** = one released batch: `case_id = plant | material | batch` (SAP `WERKS | MATNR | CHARG`).

**Event log** (`data/processed/events.csv`):

| column | meaning |
|---|---|
| case_id | plant\|material\|batch |
| activity | Manufacturing Executed, Goods Receipt, Inspection Lot Created, QC Results Recorded, Batch Record Completed, Batch Record Review, Batch Record Returned, Batch Record Corrected, Deviation Raised, Deviation Closed, Deviation Reopened, QA Disposition Review, QA Query Raised, Usage Decision |
| ts_start / ts_end | start (may be empty, see R1) and completion; milestones have start = end |
| role | Production, Warehouse, QC Lab, QA Operations, QA Compliance, QA Release (anonymised; no person-level data) |
| source_table, source_key | the row the event came from (order, material document, inspection lot, notification, MES/QMS record id) |
| start_source | explicit / status_log / milestone / none |
| match_conf | crosswalk confidence of the batch ID (1.0 for SAP tables) |
| inherited_from | parent batch for events inherited through a split/merge |

**Source mapping**

| source | activity |
|---|---|
| AFRU (order confirmations, actual start ISDD / finish IEDD) | Manufacturing Executed (first operation start → last confirmation) |
| MSEG movement type 101 | Goods Receipt |
| QALS | Inspection Lot Created (a second lot = retest) |
| QAMR (PRUEFDATUV / PRUEFDATUB) | QC Results Recorded |
| QMEL (QMDAT / QMDAB) + status log | Deviation Raised / Closed / Reopened |
| QAVE | Usage Decision (a second record = changed usage decision) |
| MES batch record (synthetic) | Batch Record Completed / Review / Returned / Corrected |
| QMS disposition (synthetic) | QA Disposition Review, QA Query Raised |

The extract fields are simplified (e.g. date and time merged into one timestamp column) and labelled SAP-style; mapping to a real extract is the first PoC step.

## KPI definitions (all deterministic)

| KPI | definition | coverage rule |
|---|---|---|
| Release cycle time | final usage decision − last order confirmation (manufacturing complete) | closed batches; open batches at cut-off are excluded and listed |
| Processing time | union of activity intervals (start..end) inside the release window: the sum of activity durations, with overlapping parallel work (QC testing and documentation review) counted once so waiting is never negative | only batches where every in-window duration activity has a start |
| Waiting time | cycle − processing | same as processing; other batches are "elapsed, unsplit" and the coverage % is shown |
| Critical-path segments | ready-for-QA − manufacturing complete, attributed to the binding path (documentation / QC results / deviation closure, whichever finished last); QA stage = last QA review end − ready-for-QA; approval = usage decision − QA review end. They telescope, so they sum **exactly** to cycle time | all closed batches |
| QA review waiting | QA stage − QA review effort | batches with QA review start times (coverage shown) |
| QC result availability | last QC result − manufacturing complete | |
| Deviation resolution time | last deviation closure − first deviation raised (per batch) | batches with deviations |
| Rework % | batches with any repeated activity: repeated batch-record review, repeated QA review, second inspection lot, reopened deviation, changed usage decision | |
| Documentation rework % | batch record returned / reviewed more than once | |
| Right first time % | no deviation AND no rework AND first usage decision = accept. Deliberately **not** 100 − rework (a test proves they differ) | |
| Hand-offs | consecutive role changes along the ordered trace | |
| Conformance % | each expected step exactly once, no exception activity (declarative rules; QC and documentation may run in parallel) | |
| Compliance % | usage decision after all QC results and deviation closures, and QA review not started before deviation closure | |

**Targets** are illustrative internal targets (oral solid 9 d; sterile 19-21 d because of the 14-day sterility test). The cycle target shown for any scope is the product-weighted mean of the batches in it. **Internal best** = best site-quarter value (≥ 20 batches) in the same product/period scope. External benchmarks are not included (they need licensed data).

**Maturity score** = Σ weight × dimension score (0-100): performance 20% (share within target), predictability 15% (1 − CV of cycle/target), quality 20% (RFT), standardization 10% (conformance), efficiency 15% (QA-waiting and hand-off scores), compliance 10%, continuous improvement 10% (share of batches produced under an intervention with a sustained, significant benefit). Score changes are attributed per dimension and sum exactly to the total change.

**Intervention test** (`analysis.intervention_effect`): pre vs post windows by manufacturing-completion date; continuous KPIs by Mann-Whitney U (medians) and rates by Fisher's exact test, 95% bootstrap CIs, plus a difference-in-differences against the site without the intervention. Exceptional events are excluded by default and the number of still-open batches in the post window is reported (right-censoring). Results are labelled **fact** (measured difference) vs **hypothesis** (causal attribution).

## Data-quality rules

| rule | behaviour | where reported |
|---|---|---|
| R1 missing start times | explicit start column → status-change log (JCDS for SAP objects, CDHDR/CDPOS style for MES/QMS records) → none = "elapsed, unsplit"; excluded from the processing/waiting split; coverage per KPI | DQ report, KPI coverage columns |
| R2 duplicates | collapsed on (case, activity, timestamp, source key) | count per source table |
| R3 re-sends vs repeats | same activity + same timestamp + new key = suspected re-send (kept out of rework, listed); same activity + new key + new timestamp = repeat / rework candidate | DQ report |
| R4 splits / merges | lineage table parent → child; children inherit upstream manufacturing events; merges take the latest parent confirmation; parents are not release cases | DQ report |
| R5 inconsistent IDs | crosswalk: normalise (case, separators, plant prefix) → exact (1.0); exact but implausible timing (0.5); edit distance 1 unique (0.85) or resolved by timing (0.8); ambiguous (0.5); unmatched (0). Included at ≥ 0.8, the rest excluded and listed | DQ report, `crosswalk.csv` |
| R6 start after end | start dropped and flagged | DQ report |

## Synthetic scenario (what the generator builds in)

Two sites, four products (two oral solids, two sterile), about 690 batches manufactured January to September 2026 (data cut-off 30 September; September is provisional because some batches are still open). Built-in effects: Site A has a longer QA queue and more documentation rework; a **documentation pre-check at Site A on 1 June 2026** (INT-01) reduces documentation rework and QA waiting; an **HVAC excursion at Site B in August** (EXC-2026-02) and a smaller supplier quarantine at Site A in March (EXC-2026-01) lengthen deviation closure for a cluster of batches. Messiness: missing starts, duplicate rows, re-sent records, splits/merges, mistyped and differently formatted batch IDs across SAP/MES/QMS.

## Tests

`tests/` (pytest, 28 tests): hand-built fixtures check every KPI exactly (cycle, processing as an interval union, waiting, segments that sum to cycle, QA waiting, rework types, RFT ≠ 100 − rework, hand-offs, coverage, open batches, sequence exception) and every data-quality rule (R1-R6, including crosswalk confidence classes and split/merge inheritance). Full-pipeline tests check maturity additivity, the intervention effect against the control site, scenario exactness, opportunity scoring, that every copilot answer is grounded in its tool results, generator determinism, and that the browser engine (`assets/engine.js`) reproduces the Python KPIs.

## Limitations

- Synthetic data; distributions are plausible but not calibrated to any real site. Field names are SAP-style and simplified.
- Framework mapping and APQC-style hierarchy are drafts; element names/IDs must be aligned to the licensed APQC PCF and the client's SOPs.
- Associations are not causation: hypotheses are labelled and come with a test. The difference-in-differences assumes parallel trends between sites.
- Bootstrap CIs in the browser use a different random stream (1,000 resamples) from Python (2,000); they agree within Monte-Carlo error.
- The copilot in this demo is deterministic (keyword routing + templates). With an LLM, routing and phrasing improve; numbers and traces stay the same.
- Effort/risk weights in the opportunity ranking are assumptions for the process owner to confirm.

## 2-minute walkthrough

1. **Framework & process** (0:00): GMP + ICH Q10 + APQC are preselected. Click **ANALYZE MY PROCESS**: health score, KPI table versus target, top issues, framework assessment (one Annex 16 row needs investigation: QA review started before deviation closure in a few batches), top 3 opportunities.
2. **Executive cockpit** (0:25): outcome KPI (mean cycle about 15 d vs 13.5 d product-weighted target) split into critical-path drivers that add up exactly. Switch "View as" to Team lead to see open batches at risk.
3. **Process explorer** (0:45): process map with the red rework loops (batch record returned → corrected → re-reviewed); switch to median waiting; bottleneck transitions; one batch traced down to SAP/MES/QMS source keys; data-quality report.
4. **KPI & benchmark** (1:05): click "QA review waiting" to drill from outcome to process to activity; note the internal best site-quarter.
5. **Challenge** (1:15): tick **Exclude exceptional events** in the filter bar; every number recalculates.
6. **Improvement & maturity** (1:25): maturity change explained per dimension; the INT-01 pre-check shows documentation rework at Site A falling from about 31% to 9% (Fisher p < 0.001) while Site B stays flat. Change the date to test any other change point.
7. **Copilot** (1:45): open a traced answer: tool, filters, SQL-equivalent query, row count, values, and the "all numbers grounded" check. Ask "Which operator causes the most deviations?" and get "Not supported by the data".
